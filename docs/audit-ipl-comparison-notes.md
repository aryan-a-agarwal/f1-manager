# IPL Simulator comparison for the F1 Manager audit

Reviewed on 25 October 2026. This is a source-backed design comparison, not a certification that every IPL feature works. No IPL source, database, or save was changed, and its test suite was inspected rather than executed. Paths beginning `IPL/` below refer to `C:/Users/10ary/Documents/programming/IPL-Simulator/`; paths beginning `F1/` refer to `C:/Users/10ary/Documents/programming/f1-manager/`.

## Method and limits

The IPL project's existing Graphify graph contains 1,626 nodes. Its graph vocabulary expanded the management-loop query to `save season calendar contract scouting development advance squad database fixture lifecycle progression`. The CLI query produced no output and was stopped; the prescribed read-only NetworkX fallback traversed the existing graph successfully, using its `edges` property. Starting nodes included `CareerCalendarFixture`, `pickSoftSquadTarget()` and `INITIAL_ACTIVE_SEASON`. The graph's source locations were used for discovery, then relevant current source was checked directly; for example, graph `CareerCalendarFixture` points to `lib/logic/careerCalendar.ts:L61`. Existing graph reflections were read. No graph rebuild, reflection write, or save-result was performed because IPL is outside the writable workspace and this comparison was read-only.

The most useful lesson is that the management game is a persistent cycle: make a decision, pay its cost, let game time progress, observe the sporting/business result, update the world, and begin another season. A menu or a rich profile does not complete that cycle by itself.

## Concrete F1 gaps identified during this comparison

1. **The displayed world is not consistently the saved world.** The headquarters function at `F1/app/game/page.tsx:364` still displays a `$142.0M` operating budget, `2027 contracts`, and `No points awarded`/`Pre-season` regardless of the saved year, transactions or standings. It also renders `team.drivers`, while career workforce lineups can change. Derive these cards from the current career and use one currency convention. `F1/app/game/page.tsx:130` and `:137` store shortlist names under the global key `f1-manager-shortlist`; these are not scoped to a career and names are not durable IDs.

2. **The yearly rollover is currently much narrower than the management model.** `F1/lib/career/seasonLifecycle.ts:22` updates workforce lineups, calendar, clock, weekend operations and championship. It preserves the remaining career wholesale. There are no calls there to annual finance close/open, sponsor expiry, driver/staff aging or development, retirement, new prospects, annual objectives, rival development, or new-year ATR processing. These need explicit transition ownership, rather than assuming a new calendar makes the next season complete. `F1/lib/career/workforce.ts:8` copies prior lineups forward when a year has no lineup; that is a useful continuity fallback, not a complete competitive off-season market.

3. **Scouting and personnel development are currently shallow.** `F1/lib/career/paddockMarket.ts:556` seeds `scoutedProspects` by taking the static free agents; there is no assignment/report/progression engine in that module. `F1/lib/career/types.ts:585` only gives the market staff and scouted-prospect arrays alongside drivers. Existing F1 recruitment should be expanded, not replaced: `F1/lib/career/paddockMarket.ts:582` and `:713` already implement driver/staff contract actions.

4. **Finance needs settlement discipline.** F1's transaction helper at `F1/lib/career/finance.ts:105` creates a new random timestamp-based transaction ID (`:117`) for every call and updates cash and cap totals directly. It provides no business-source ID deduplication at this boundary. The initial finance state has illustrative transactions and fixed monthly projections (`:35`, `:89`) and team-key mismatches such as `red_bull` versus grid `red-bull` (`:23`). Consolidate the ledger and scheduled obligations, verify monetary assumptions and team IDs, and add annual lifecycle behavior before layering more finance screens on top.

5. **Race results do not yet express management investment.** `F1/lib/career/sessionEngine.ts:65` ranks entrants using its private `driverBaseRatings` table plus a seeded variation, not current market skills, car parts, facilities, staff or strategy. It assigns fixed race/sprint lap totals (`:75`). This is adequate as a temporary pipeline exercise, but spending money cannot currently deliver a representative sporting payoff through this engine. Keep the fast-result interface for early management validation; feed it current driver/car state before judging game balance. Full simulation and race control remain the final stage, as requested.

6. **Save scale should be solved before race telemetry.** F1 already has validation, schema migration, fallback backup, import/export helpers and tests (`F1/lib/career/storage.ts:44`, `:69`, `:109`, `:115`; `F1/calibration/careerSave.test.ts:29`). However the primary save and backup are single localStorage keys (`:5`, `:6`), and each save serializes the whole career (`:60`). IPL is a useful reference for career identity, archive separation, quota tests and write batching. Multiple slots and cloud synchronization are optional product decisions; save integrity and clear failures are core requirements.

## What should not be copied from cricket

- Auctions, retention lists, bidding purses, right-to-match mechanics, overseas-player quotas, and batting/bowling roles are cricket mechanisms. F1 needs seats and specialist posts, driver/staff contracts, effective dates, buyouts, reserve/academy status and any eligibility rules from the chosen ruleset.
- Cricket fixtures, league tables, net run rate, knockout brackets and scorecards do not map directly to a Grand Prix championship. F1 needs distinct practice/qualifying/sprint/race sessions where applicable, grid formation, classification, points/countback and both driver and constructor standings.
- Home-stadium ownership and pitch preparation are not a sound default business model for a constructor. Use factory and simulator investment, design/manufacturing capacity, freight/travel, technical suppliers and sponsorship. Circuit characteristics are normally event inputs, not surfaces the team edits to its advantage.
- A cricket player-performance engine cannot become a race engine by renaming ratings. Racing requires interactions among driver, car, tyres, fuel/energy, track, weather, traffic, strategy and regulations. Detailed racing and race control should use the existing session interface as an integration boundary, built after management systems are coherent.
- Do not copy IPL's large page/store organization. `IPL/lib/store/gameStore.ts` and `IPL/app/game/overview/page.tsx` each contain thousands of lines. Retain F1's domain modules, extract its large UI page into feature components, and keep simulation/business decisions out of rendering code.

All numerical sporting and financial limits should be stored in a versioned season ruleset and verified against the applicable official regulations. This comparison does not assert that the game's existing numerical constants are correct for 2027.

## Suggested dependency order

1. **Coherent foundation:** canonical IDs/data ownership, save integrity, current-state UI, explicit fictional-versus-verified baseline data and stable ruleset version. Acceptance: all screens agree after a hire, expense, date change and reload.
2. **One management time pipeline:** blockers, deadlines, scheduled payments, projects, facility upkeep, contract activation and event messages processed once. Acceptance: one-day steps and a date jump give equivalent state; retry/reload does not charge or complete twice.
3. **Operational management:** contracts/roles, meaningful R&D and facilities, scheduled finance, sponsors/board objectives and seeded rival behavior. Acceptance: each management action has a cost, time consequence and visible persisted outcome.
4. **Durable multi-season loop:** accounting close/open, expiry/renewal, aging/development, AI seat/staff decisions, prospect intake, season archives and new objectives. Acceptance: at least three automated full seasons complete, reload correctly and retain coherent cash, contracts and histories.
5. **Management depth and usability:** scouting uncertainty, training/academy, recruitment negotiation history, staff delegation, forecasts and readable news/decision feedback. Some of these can move earlier if required for a chosen minimum playable scope; none should delay fixing the management loop.
6. **Final stage — full race simulation and race control:** validate engine inputs and versioned outputs; build practice/setup, qualifying, tyre/energy/traffic/weather race dynamics, AI tactics and live controls; then add the authority/state machine for flags, safety car/VSC/red flag procedures, restarts, penalties, classification and result corrections. Persist and resume live sessions and calibrate outcomes across seeds. Keep race-director actions separate from the player's team strategy commands unless a separate sandbox/director mode is explicitly intended.

The main game readiness gate is a repeatable management career across multiple seasons with visible consequences and reliable saves. Advanced racing should deepen that functioning game.
